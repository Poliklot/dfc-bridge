## Макет, который не приходится расшифровывать

**Подготовьте макет так, чтобы сам файл отвечал на вопросы разработчика.**

DFC Bridge — методология подготовки понятных макетов. Разработчик или ИИ должен видеть, какие экраны связаны, какие слои обозначают один и тот же элемент и что делает каждая кнопка, а не угадывать это по внешнему виду.

## Минимальный пример

Кнопка «Связаться» есть в широкой и узкой версии главной страницы. Дайте ей одинаковое стабильное имя и укажите одно и то же реальное модальное окно. Ниже — имена слоёв Figma; части в квадратных скобках — теги, а не видимый текст кнопки:

```text
home [page=home] [route=/] [bp=1440] [view=default]
  hero [section=home-hero]
    contact-button [action=modal:contact-modal]
  contact-modal [modal=contact-modal]

home [page=home] [route=/] [bp=375] [view=default]
  hero [section=home-hero]
    contact-button [action=modal:contact-modal]
  contact-modal [modal=contact-modal]
```

Теперь видно: `contact-button` — одна и та же кнопка на обеих ширинах, она должна открывать `contact-modal`. Само расположение задаётся средствами Figma. Тег действия описывает намерение, но не создаёт связь в прототипе и не реализует модальное окно. Это фрагмент имён, а не готовый макет: состояния окна, способ закрытия и расположение ещё нужно подготовить и проверить.

## Основная идея

Храните каждое решение там, где ему место:

1. **Настройте настоящую структуру в Figma.** Используйте иерархию, Auto Layout, компоненты, варианты и параметры расположения. Не переписывайте эти свойства вручную в метаданные.
2. **Добавьте стабильные имена и короткие теги для смысла.** Имена связывают один и тот же элемент на разных ширинах. Теги обозначают страницу или секцию, адрес ссылки, действие, состояние или намеренное исключение.
3. **Используйте структурированные данные `bridge`, когда коротких тегов недостаточно.** Например, для схемы данных, поведения по условию, требований доступности или другой композиции на узком экране. Здесь же фиксируются открытые вопросы и свидетельства поставки. Не превращайте имя слоя в длинную анкету.

По умолчанию один и тот же элемент сохраняет ключ и логического родителя на подготовленных ширинах. Если композиция меняется, явно опишите соответствие элементов, а не подменяйте дерево незаметно. Нерешённые вопросы запишите, а не заменяйте выдуманными ответами.

Методология не привязана к конкретному редактору, фреймворку, системе управления содержимым или среде выполнения. Один и тот же контракт можно реализовать в вебе, мобильном приложении, внутреннем редакторе, инструменте без кода или автоматизированном процессе с участием ИИ.

## Что даёт методология

Макет, подготовленный по DFC Bridge, можно открыть без автора и понять:

1. какую страницу и какое состояние он описывает;
2. какие фреймы являются адаптивами одной страницы;
3. какие элементы соответствуют друг другу на разных ширинах;
4. куда ведут ссылки и что делают элементы управления;
5. что является контентом, декором или экспортируемым ресурсом;
6. какие ограничения сделаны намеренно.

Перед передачей решения, относящиеся к макету, должны быть доступны и проверяемы. Нерешённые вопросы нужно записать и указать ответственного, а не скрывать. Проверка макета без замечаний не доказывает, что реализация работает.

**Без слепых зон** не означает, что каждый ответ известен сразу. Важное неизвестное явно записано, имеет область, владельца, блокирующий статус, точку пересмотра и безопасный запасной путь.

## Инструменты

DFC Bridge — методология, а не инструмент или адаптер для конкретной платформы. Её можно применять без плагина.

[DFC Bridge Assistant](https://www.figma.com/community/plugin/1654485530503673254) — необязательный вспомогательный Figma-плагин. Его устанавливаемая версия публична в Figma Community, а репозиторий реализации является приватным. Методология, документация, схемы, чеклисты и каталог правил в этом репозитории остаются открытыми по лицензии MIT.

Каталог содержит **107 правил**. Публичные манифесты покрытия фиксируют два точных и несуммируемых набора выдаваемых правил: Page Check охватывает **42** (40 автоматически и 2 эвристически), а проверка выбранной секции — **26** (24 автоматически и 2 эвристически; 20 локальных и 6 для выбранных вариантов). Оба набора включают блокирующие правила структуры; структурированное и ручное покрытие остаётся явным.

## Локальная разработка

Используйте версию Node.js из [`.nvmrc`](.nvmrc), затем установите зависимости строго по lock-файлу:

```bash
nvm use
npm ci
npm run dev
```

Перед запросом на слияние запустите полную проверку:

```bash
npm test
npx playwright install chromium # только перед первым локальным запуском
npm run test:e2e
npm audit
```

Канонический контент на английском, русском и китайском находится в `docs/`, `docs/ru/`, `docs/zh/` и `examples/`. Не редактируйте сгенерированные файлы в `src/content/docs/`: команда `npm run content:sync` пересоздаёт их из [`validator/site-content.json`](validator/site-content.json). Для проверки сборки в корне используйте `SITE_BASE=/ npm run build`.

Правила изменения контракта и полный процесс ревью описаны в [CONTRIBUTING.md](CONTRIBUTING.md), а история публичных выпусков методологии — в [CHANGELOG.md](CHANGELOG.md).

## Название и шесть принципов

**DFC Bridge — Design Frontend Contract** — единое публичное название. В разговоре остаётся «Бридж». Продукты называются **DFC Bridge Assistant** и **DFC Bridge Explorer**, технические имена — `dfc-bridge` и `dfc-bridge-*`. Bridge обозначает мост между намерением дизайнера и реализацией. Макет перестаёт быть отдельной картинкой и становится системой, которую можно последовательно воспроизвести в другой среде.

Шесть принципов сохраняют мнемонику Bridge:

| Буква | Каноническое название | Смысл |
| --- | --- | --- |
| **B** | **Breakpoints** | Адаптивы и контрольные ширины заданы явно. |
| **R** | **Roles** | Назначение значимого слоя понятно из структуры Figma, компонента или DFC Bridge-тега. |
| **I** | **Identity** | По умолчанию элемент сохраняет идентификатор и родителя; изменение композиции требует явного сопоставления. |
| **D** | **Dependencies** | Ссылки, действия, модальные окна, состояния и их цели связаны явно. |
| **G** | **Geometry** | Положение, размеры, отступы и параметры текста можно воспроизвести. |
| **E** | **Exceptions** | Фиксированные размеры, переполнение, экспорт и нестандартное поведение имеют объяснимую причину. |

Английские названия сохраняются только потому, что образуют слово Bridge. В русской документации используются понятные русские формулировки. Полный словарь приведён в разделе [«Терминология»](docs/ru/18-terminologiya.md).

## Словарь бренда

В английских материалах и названиях продуктов используются следующие обозначения:

- **DFC Bridge-ready design** — макет, подготовленный по DFC Bridge;
- **DFC Bridge Contract** — структурированный контракт переноса;
- **DFC Bridge Preflight** — проверка макета перед передачей;
- **DFC Bridge Adapter** — адаптер для конкретной среды реализации;
- **DFC Bridge Linter** — автоматическая проверка макета;
- **DFC Bridge Exception** — намеренное исключение с явно указанной причиной.

В обычном русском тексте следует использовать русские описания, а не смешанные конструкции вроде «DFC Bridge-ready чеклист».

Знак DFC Bridge следует тому же контракту: шесть стабильных модулей обозначают шесть принципов и складываются в одну узнаваемую форму. Смысл, цвета, охранное поле и исходники описаны в разделе [«Бренд-система»](docs/ru/brend-sistema.md).
