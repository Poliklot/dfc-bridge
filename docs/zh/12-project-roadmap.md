# 状态与路线图

**状态快照：2026 年 10 月 13 日。** DFC Bridge 是采用 MIT 许可证的公开方法论与开源文档、验证器仓库。DFC Bridge Assistant 可从 Figma Community 安装，但其实现仓库仍为私有。公开安装不代表插件源代码、问题跟踪或发布记录也已公开。

## 当前可用

<a id="完整的传输方法"></a>

### 完整的交付方法

规范涵盖：

- 简短设计标记及角色、模板、设计实例、运行时数据、目标实现五类标识映射；
- 视口和容器响应式行为、流式规则及声明的结构转换；
- 内容、数据展示、表格、网格、图表、来源、格式和失败状态；
- 状态机、表单、异步行为、焦点、URL、历史及恢复；
- 动效、长滚动、反向和重新进入、减少动态效果及替代方案；
- WCAG 2.2 AA 无障碍配置、RTL、双向文本和平台能力；
- 设计、契约、实现、QA、发布和偏差管理；
- 有负责人的待解决问题，避免未记录的未知项。

<a id="结构化合约和验证工件"></a>

### 结构化契约与验证资料

0.9 版引入了尚未稳定为 1.0 的[结构化交付契约](04-transfer-contract.md)和 [JSON Schema](../validator/bridge.schema.json)。0.10 版增加了源设计中原生 Auto Layout 与 GROUP 边界的阻塞规则。0.11 版增加了选定区块边界、旧有宿主契约、本地与待验证证据，以及限定范围的就绪状态。仓库还提供：

- 简短图层标签的规范注册表；
- 英俄双语规则目录；
- 模式与可验证样本；
- 方法论、Page Check 和选定区块的覆盖清单；
- 本地化、引用、示例、覆盖和网站内容检查。

结构化元数据补充 Figma 原生信息及简短标签，并不意味着已经存在通用的生产级适配器。

### 可公开安装的 Figma 助手

[从 Figma Community 安装 DFC Bridge Assistant](https://www.figma.com/community/plugin/1654485530503673254)。公开覆盖快照支持页面直接子项和原生 SECTION 内的页面根，以及独立的选定区块源检查，不需要另外注册 DFC Bridge 账号。Community 发布需单独手动完成，因此可安装版本应在安装页确认。

插件实现仓库、私有问题及内部发布记录不属于公共方法论资料。安装状态看 Community；公开契约、规则、示例和计划看本仓库。

## 独立的自动化范围

规则目录共有 **107 条规则**。公开覆盖快照记录两种不能相加的检查范围：

- **Page Check：**可报告的规则 ID 共 **42** 个，其中 **40 个自动检查**、**2 个启发式检查**，见 [Page Check 覆盖清单](../validator/page-check-coverage.json)。
- **Check selected section：**可报告的规则 ID 共 **26** 个，其中 **24 个自动检查**、**2 个启发式检查**；20 个在本地范围检查，6 个仅在明确选择的可比较变体之间运行，见[选定区块覆盖清单](../validator/section-check-coverage.json)。

两个集合存在重叠，不能相加。区块清单还明确列出不会报告的页面、文件规则，以及需要另行验证的文件和集成问题。

覆盖范围外的规则不是“漏报的错误”。其中许多需要人工判断产品含义、内容、无障碍、平台能力、性能或生命周期。[方法论覆盖清单](../validator/methodology-coverage.json)说明自动、启发式和人工检查的责任。

因此：

- Page Check 无问题，只表示声明的页面范围检查通过；
- 选定区块 Ready，只表示其源设计在请求的上下文中就绪；
- 适用范围内仍需完整清单、结构化契约验证、人工审查、目标实现 QA 和偏差审查；
- 不得声称全部 107 条规则已自动执行，也不得把区块源就绪说成宿主页面或产品就绪。

## 已知的限制

<a id="pre-10-schema-compatibility"></a>

### 1.0 之前的模式兼容性

0.9 引入的结构化契约已可使用并有版本，但尚未冻结。数据生产方和消费方必须固定 `contractVersion`，明确拒绝不支持的结构，并在迁移时保留稳定标识和需求链接。

### 没有通用适配器

DFC Bridge 定义平台无关的意图和能力配置，目前没有一个适配器能为所有 Web、原生平台、无代码工具、编辑器和设计系统生成生产级结果。

### 源工具检查是有意限定范围的

Page Check 检查选定页面或根。Check selected section 仅解析明确选择的 `[section]` 边界，不遍历旧有同级节点，并将需要文件或宿主查找的依赖交给后续验证。完整有效的外部 href 在源检查中已确定目的地；所选根本身为 `INSTANCE` 时结果为 Partial，普通后代组件实例则作为可信的整体边界，不降低 Ready。两种模式都不能证明运行时数据、浏览器历史、屏幕阅读器输出、性能预算、后端行为或生产环境符合性。

<a id="代表性示例并非详尽的产品决策"></a>

### 示例不能代替产品决策

方法论说明如何记录数据、状态、动效、无障碍、能力和生命周期决策。每个产品仍需提供自己的具体值、负责人、支持平台、预算和安全替代方案。

## 1.0之前

1. 稳定结构化契约，发布兼容与迁移策略。
2. 只在能明确说明自动、启发式或人工证据边界时扩展验证器。
3. 增加覆盖更多平台、数据展示、有状态流程、动效、RTL 和能力配置的完整可验证样本。
4. 定义适配器认证所需的模块、替代方案、偏差及测试证据。
5. 维护公开变更日志，并记录方法论、模式和规则的决策。
6. 继续开展可衡量的试点，记录准备成本、追问减少量、缺陷及无障碍结果。

## 1.0之后

可能的方向包括平台专用适配器、更深入的源工具检查、设计系统映射、报告和生态集成。在明确范围、负责人并正式发布前，它们都只是计划。
