# 设计师清单

在把 Figma 文件交给开发前使用这份简短清单。如果某一项需要详细决定，请打开对应指南，不要一次读完整规范。

## 先选择范围

你可以交付：

- 包含准备好宽度的一整页；
- 或现有产品中的一个明确标记新区块。

不要为了检查一个区块而给现有产品添加页面元数据。[团队落地指南](19-team-adoption.md)说明了这种情况。

## 页面和宽度

交付整页时检查以下三项。只交付区块时，确认其 `[section=...]` 根和本次交付的上下文；不要要求页面标签，也不要编造未请求的变体。

- [ ] 从根图层可以看出页面、已知的真实路径、宽度和状态。
- [ ] 准备好的根图层描述同一页面，并保持相同含义。
- [ ] 同一个逻辑元素在不同宽度中使用同一个名称。

参见[响应式行为](03-responsive-breakpoints.md)。

## 名称和关系

- [ ] 重要图层使用简短的英文 `kebab-case` 名称。
- [ ] 名称中没有设备或宽度后缀。
- [ ] 相关图层通过有意义的父级连接，而不是只靠视觉位置。

参见[图层命名](02-layer-naming-and-identity.md)和[设计规则](01-design-rules.md)。

## 链接、动作和状态

- [ ] 每个链接都有已知的 `[href=...]`，或使用草稿 `[link]` 并记录待解决问题及负责人。
- [ ] 每个界面变化都有 `[action]` 和存在的目标。
- [ ] 重要的默认、加载、空、错误和成功状态已经展示或说明。

参见[交互](05-interactions-and-targets.md)和[状态反应](22-state-machines-and-reactions.md)。

## 内容和组件

- [ ] 文本、价格、图片和列表可以承受真实数据与本地化。
- [ ] 内容、装饰和可导出资源彼此可区分。
- [ ] 组件来自正确的库，并在需要时保持可编辑。

参见[组件](14-components-and-ui-kit.md)和[内容与溢出](07-height-and-overflow.md)。

## 交付检查

- [ ] 没有参与制作的人无需会议就能找到交付的页面或区块、上下文、动作、目标和可编辑资源。

如果答案仍在聊天记录中，请把它补充到文件，或记录为有负责人的待解决问题。在 [DFC Bridge Assistant](https://www.figma.com/community/plugin/1654485530503673254) 中，整页运行 **Check page**，所选区块根运行 **Check selected section**。修正后重新检查，并保留外部依赖及其负责人。源文件报告无问题，不代表宿主页面或实现已通过验收。

## 需要严格检查时

只有在团队需要完整审计数据、无障碍、动效、实现和发布决定时，才打开[完整检查](08-preflight-checklist.md)。
